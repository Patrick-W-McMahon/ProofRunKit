# Windows x86 installer (MSI)

This page records how to build and inspect the 32-bit MSI (#38) and the MSVC
Win32 presets plus 32-bit Assembly path that feed it (#39). The installer
technology (WiX Toolset v4 MSI) and the deferred signing decision are the same
as for x64; see [installer-windows-x64.md](installer-windows-x64.md) (#40, #41).

There are no GitHub Actions workflows; the MSI is built locally from the
`windows-msvc-x86-release` preset.

## Decisions

| Topic | Decision | Ticket |
| --- | --- | --- |
| Technology | **WiX Toolset v4** MSI, pinned to **4.0.6**, `wix build -arch x86`. | #40, #38 |
| Install scope | Per-machine. | #36, #38 |
| x86 destination | `ProgramFilesFolder\ProofRunKit`. On 64-bit Windows that is `%ProgramFiles(x86)%\ProofRunKit` (typically `C:\Program Files (x86)\ProofRunKit`). On 32-bit Windows it is `%ProgramFiles%\ProofRunKit`. **Not** `C:\Windows\SysWOW64`. | #38 |
| PATH | Optional feature **AddToPath**, **included by default**. | #38, #40 |
| Start Menu | A "ProofRunKit (32-bit)" folder, so it does not collide with the 64-bit Start Menu folder. | #38 |
| Add/Remove Programs | Name **`ProofRunKit (32-bit)`**, publisher `ProofRunKit`, same repo URL. The distinct name keeps the 32-bit and 64-bit entries readable when both are installed. | #38 |
| Signing | **Deferred.** Packages ship unsigned. | #41 |
| Packers | None. Ordinary MSI cabinet compression only. | #22 |
| Calling convention | 32-bit **cdecl**. `.model flat, C` in `src/asm/x86_windows.asm` so `PROC` emits the leading underscore. A 64-bit result is returned in EDX:EAX, which is also what RDTSC writes. (A project-wide CODE_STANDARDS.md remains #6.) | #39 |

The 32-bit and 64-bit products can be installed side by side: they use different
UpgradeCodes, different ProductNames, and different Program Files folders.

## UpgradeCode

The x86 product line uses this UpgradeCode. **Do not change it**, and do not
reuse the x64 value `{FB358981-835D-421D-8634-BA130FE100A2}`.

```
{A31020BF-969A-4139-9FA1-82E044AC31F5}
```

`ProductCode` is generated by WiX on every build. ProductVersion comes from the
CMake project version (`0.1.0` today). A newer 32-bit installer refuses to
downgrade.

## What is installed

| Item | Location |
| --- | --- |
| `proofrunkit.exe` (32-bit) | `%ProgramFiles(x86)%\ProofRunKit` on 64-bit Windows; `%ProgramFiles%\ProofRunKit` on 32-bit Windows |
| `LICENSE.txt` | Same folder. The repo-root [`LICENSE`](../LICENSE) (verbatim Apache License 2.0), packaged unchanged (#58). |
| `NOTICE.txt` | Same folder. The repo-root [`NOTICE`](../NOTICE), per Apache-2.0 section 4(d) (#58). |
| Start Menu shortcuts | `ProofRunKit Help (32-bit)` and `ProofRunKit on GitHub.url` under "ProofRunKit (32-bit)" |
| Optional PATH entry | The install directory is appended to the **system** PATH |

`proofrunkit_selftest`, PDBs, static libraries, and project test suites are **not**
packaged. The 32-bit hot path is MASM (`ml.exe`, `asm-masm-x86`) with the same
portable C fallback as x64.

## Silent install, uninstall, and logging

Run from an elevated command prompt. `/qn` is fully silent; `/qb` shows a progress
bar; `/l*v` writes a verbose log.

```bat
rem Install, including PATH (the default)
msiexec /i ProofRunKit-0.1.0-win-x86.msi /qn /l*v %TEMP%\ProofRunKit-x86-install.log

rem Install without adding PATH
msiexec /i ProofRunKit-0.1.0-win-x86.msi /qn REMOVE=AddToPath

rem Uninstall this MSI (or use Add/Remove Programs)
msiexec /x ProofRunKit-0.1.0-win-x86.msi /qn

rem Upgrade: install a newer 32-bit MSI with the same UpgradeCode
msiexec /i ProofRunKit-0.2.0-win-x86.msi /qn
```

## Prerequisites

In addition to the [Windows build prerequisites](building-windows.md) (Visual Studio
2026 with the C++ workload — this includes `ml.exe` as well as `ml64.exe` — CMake
3.21+, Git), the MSI needs the same WiX v4.0.6 tool and UI extension as x64.
The scripts do not install those tools; they print the commands if they are missing.
See [installer-windows-x64.md](installer-windows-x64.md) for the exact
`dotnet tool install --global wix --version 4.0.6` lines. The .NET SDK (6 or later;
8 recommended) is required to install that tool.

Enter a 32-bit developer shell on a 64-bit machine with
`Launch-VsDevShell.ps1 -Arch x86 -HostArch amd64`.

## Building the 32-bit binary and the MSI

From the repository root, after the working tree is clean:

```powershell
.\installer\build-x86.ps1
.\installer\build-msi-x86.ps1
```

`build-x86.ps1` configures, builds, and CTests `windows-msvc-x86-debug`. It aborts
if the working tree is dirty (it never stashes, resets, or discards changes) and
it does not switch branches.

`build-msi-x86.ps1` configures and builds `windows-msvc-x86-release`, then builds
the `package-msi` target and prints the output path:

```
build\windows-msvc-x86-release\installer\ProofRunKit-<version>-win-x86.msi
```

The same steps by hand:

```powershell
cmake --preset windows-msvc-x86-debug
cmake --build --preset windows-msvc-x86-debug
ctest --preset windows-msvc-x86-debug --output-on-failure

cmake --preset windows-msvc-x86-release
cmake --build --preset windows-msvc-x86-release
cmake --build --preset windows-msvc-x86-release --target package-msi
```

`cmake --build --preset windows-msvc-x86-msi` is equivalent to the last command.
The self-test asserts that `prk_get_cycle_counter_implementation_name()` is
`asm-masm-x86` when the Win32 Assembly path is selected.

## Verifying without installing

```powershell
.\installer\verify-msi-x86.ps1
.\installer\verify-msi-x86.ps1 -MsiPath path\to\ProofRunKit-0.1.0-win-x86.msi
```

This is read-only: it never runs `msiexec /i`. It uses the same Windows Installer
COM helpers as the x64 verifier (including the PowerShell 5.1 fixes in #50–#53)
and checks that:

- the Summary Information template is `Intel;1033` (not x64)
- there is no `VersionNT64` launch condition
- `INSTALLFOLDER` is `ProgramFilesFolder\ProofRunKit`
- the product name is `ProofRunKit (32-bit)` and the UpgradeCode is the x86 value above

An administrative extraction (`msiexec /a`) then confirms `proofrunkit.exe`,
`LICENSE.txt` and `NOTICE.txt` are present (and match the repo-root files). The administrative `TARGETDIR` is only a temporary
unpack folder.
